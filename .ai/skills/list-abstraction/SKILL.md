# Skill: TableSearch List Abstraction

## When to Use
Use this skill when you need to:
- Refactor a `TableSearch()` case in a page module
- Create a new list view for an entity
- Remove HTML/JS embedded in SQL queries

## The Problem

Every module has a `TableSearch()` method with cases like:
```php
case 'artikel_list':
    $allowed['artikel'] = ['list'];
    $heading = ['', 'Nr.', 'Bezeichnung', 'Preis', 'Menü'];
    $width = ['1%', '10%', '50%', '15%', '5%'];
    $findcols = ['a.id', 'a.nummer', 'a.bezeichnung', 'a.preis'];
    $searchsql = ['a.nummer', 'a.bezeichnung'];
    $menu = "<a href=\"...%value%\"><img src=\"...edit.svg\"></a>...";
    $sql = "SELECT SQL_CALC_FOUND_ROWS a.id,
            CONCAT('<input type=\"checkbox\"...>') as wahl,
            a.nummer, a.bezeichnung,
            FORMAT(a.preis, 2) as preis,
            a.id FROM artikel a";
    // ... 50+ lines of repetitive setup
```

## The Solution: Declarative List Configuration

### Step 1: Create a List Configuration

```php
// In the module class or a separate config file
public function getListConfig(string $name): ListConfig
{
    return match($name) {
        'artikel_list' => new ListConfig(
            table: 'artikel',
            alias: 'a',
            columns: [
                ListColumn::checkbox('id'),
                ListColumn::text('nummer', 'Nr.', width: '10%', searchable: true),
                ListColumn::text('bezeichnung', 'Bezeichnung', width: '50%', searchable: true),
                ListColumn::money('preis', 'Preis', width: '15%'),
                ListColumn::actions('id', [
                    Action::edit('index.php?module=artikel&action=edit&id=%id%'),
                    Action::copy('index.php?module=artikel&action=copy&id=%id%'),
                    Action::delete('index.php?module=artikel&action=delete&id=%id%'),
                ]),
            ],
            defaultSort: 'nummer ASC',
            where: 'a.aktiv = 1',
        ),
        // ... other list configs
    };
}
```

### Step 2: Use the ListRenderer

```php
// In the module action method
public function ArtikelList(): void
{
    $config = $this->getListConfig('artikel_list');
    $renderer = $this->app->Container->get(ListRenderer::class);
    $renderer->render($config, $this->app->Tpl);
}
```

### Step 3: The ListRenderer Handles Everything

The `ListRenderer` class (to be created in `classes/Components/UI/ListRenderer.php`) handles:
- SQL generation (with prepared statements)
- HTML generation (outside of SQL!)
- JavaScript (DataTables init, filter functions)
- Pagination
- Column sorting
- Search functionality

## Migration Strategy

1. Pick a simple module with a basic list (e.g., `gruppen`, `einheiten`)
2. Create the `ListConfig` and `ListRenderer` classes
3. Refactor one `TableSearch()` case at a time
4. Keep old cases working during transition

## Key Principle

> SQL should return DATA, not HTML. HTML should be generated by the Renderer, not by the database.

## Rules

- ✅ SQL returns only raw data columns
- ✅ Actions/menus are defined as configuration, not as HTML strings
- ✅ Checkboxes, icons, formatting are Renderer responsibilities
- ❌ No `CONCAT('<input...')` or `CONCAT('<a href...')` in SQL
- ❌ No `onclick="..."` in SQL-generated HTML
